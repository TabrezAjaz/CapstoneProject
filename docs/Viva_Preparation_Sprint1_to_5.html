A. Project overview & architecture

Sabse zyada poocha jaane wala section. Har answer 20–40 second mein bol sako, itna rakho.

Apna project ek line mein kya hai?Architecture

Answer: Ye ek automated container image vulnerability scanner hai jo Trivy se images scan karta hai, severity threshold ke aadhaar par CI/CD build ko pass ya block karta hai, aur structured JSON/HTML/PDF reports ke saath Slack alerts bhejta hai.

Problem statement: Containerised apps mein known vulnerabilities production tak pahunch jaati hain kyunki scanning ya manual hai ya pipeline mein missing hai. Iska result — insecure image deploy ho jaati hai, aur pata bhi nahi chalta.

Solution: Ek hi policy engine (Python) jo local, GitHub Actions aur Jenkins — teeno jagah same decision deta hai.

Agar Trivy already CI mein chal sakta hai, to Python wrapper kyun banaya?Architecture

Ye important question hai. Wrapper ke 5 clear faayde hain:

  1. Ek hi policy engine: Threshold, severities, ignore-unfixed — sab config se aata hai. Agar Jenkinsfile aur GitHub YAML do jagah logic hoti, to dono drift kar jaate.
  2. Stable exit contract: Trivy ka exit code scanner failure aur policy decision mein farq nahi batata. Wrapper 0/1/2/3 deta hai — jisse "image vulnerable hai" aur "scanner toot gaya" alag dikhte hain.
  3. Normalised output: Trivy ka JSON bahut bada aur version-dependent hai. Wrapper usko ek chhote, versioned schema (1.0) mein convert karta hai jise report generator reliably consume kar sakta hai.
  4. Artifact + metadata: scan_id, UTC timestamp, CI source — ye sab wrapper add karta hai, jisse traceability milti hai.
  5. Config validation: Galat threshold ya timeout par fail-closed (exit 2) hota hai, silent fallback nahi.
config.yaml kyun? Hardcode kyun nahi kiya?Architecture

Hardcode karne se har change ke liye code edit + commit + review chahiye hota, aur environment-specific values code mein aa jaate.

Config file se:

  • Same code local, CI aur Jenkins — sab jagah chalta hai
  • Review mein policy change clearly visible hota hai (code review, not buried in YAML logic)
  • Secrets config mein nahi rakhe — sirf policy. Webhook sirf environment/credential se aata hai.

Python wrapper Sprint 1 mein kya karta tha?Sprint 1

Ye Trivy ke around ek thin, testable layer thi. Functions:

  • load_config() — config.yaml load + safe defaults
  • scan_image() — Trivy JSON mode mein chalata tha aur parse karta tha
  • write_artifact() — normalized artifact likhta tha
  • run() / main() — CLI entry point

Design choice: wrapper deliberately "ek kaam achhe se" karta hai. Sprint 2 mein usme policy add hui, Sprint 3 mein reporting — core scan logic badla nahi.

Sprint 1 mein kaunsi problem aayi aur kaise solve ki?Sprint 1

Do real issues aaye — ye batana achha lagta hai kyunki debugging dikhata hai:

  1. Java DB download failure (disk space): node:18/nginx scan ke waqt Trivy Java DB (~913 MB) download karne laga aur disk full ho gaya.
    Fix: scan scope OS packages tak limited kiya (JAR scanning off), aur --timeout badha ke 15m kiya. Yaani problem diagnose karke requirement ke hisaab se scope tune kiya.
  2. Scanner timeout on large images: node:18 mein 413 packages the aur default timeout kam pad gaya.
    Fix: SCANNER_TIMEOUT config se controllable banaya (default 15m).

Bonus: ek bug bhi mila — wrapper purane version mein non-zero exit code par bhi empty result return kar sakta tha (silent false-negative). Usko fix karke fail-fast bana diya: ab Trivy fail ho to exit 3, aur wrapper ko zero-vulnerability nahi samjhega.

--ignore-unfixed kya karta hai? Aapne use kiya ya nahi?Sprint 1

--ignore-unfixed un vulnerabilities ko hide karta hai jinka koi fix version available nahi hai. Yaani sirf wahi dikhata hai jinko upgrade karke actually fix kar sakte ho.

Humara default: ignore_unfixed: false — kyunki hum poora risk dekha rahe hain, aur "unfixed" vulnerabilities bhi security risk hain (bas unka mitigation alag hota hai, jaise compensating control ya image replace).

Override: CLI par --ignore-unfixed ya env var SCANNER_IGNORE_UNFIXED=true se change ho jaata hai — per-run flexibility milti hai.

Scan results reproducibility kaise ensure karte ho?Sprint 1
  • Trivy version pinned: 0.74.0 (na ki latest) — CI aur local same engine
  • Scan options artifact mein record: severities, pkg_types, ignore_unfixed, timeout — "kaise scan hua" documented
  • UTC timestamps: scanned_at se pata chalta hai kis DB snapshot par scan hua
  • Checksums: report manifest mein SHA-256, isliye report tamper ya corruption detect ho sakti hai
  • Note: exact finding counts time ke saath badalte hain (naye CVEs add hote hain), isliye tests mein synthetic fixtures use kiye — real CB data par assert nahi karte.

C. Sprint 2 — CI/CD security gate

Yahi sabse technical sprint hai. Exit codes aur precedence par examiner zaroor poochega.

Sprint 2 ka goal kya tha?Sprint 2

Assignment: scanning ko CI/CD pipelines (Jenkins, GitHub Actions) mein automate karna, severity ke aadhaar par pass/fail criteria define karna, environment configuration add karna, aur sample images ke saath integration test karna.

Goal: image vulnerabilities hone par build automatically fail ho jaaye — yaani scanner ek enforcement point ban jaaye, sirf reporting tool nahi.

Build exactly kab fail hota hai?Sprint 2

Policy: fail_on: HIGH. Yaani:

  • Koi bhi HIGH ya CRITICAL finding → build block (exit 1)
  • Sirf MEDIUM/LOW → build pass (exit 0), par report mein dikhta hai
  • Scanner/config problem → build fail (exit 2 ya 3), fail-closed

blocking_count() function threshold ke barabar ya upar wale findings count karta hai — severity ranking: UNKNOWN < LOW < MEDIUM < HIGH < CRITICAL.

Practical example: alpine:3.19 par 2 HIGH findings mile → blocking_findings=2 → exit 1 → build red.

Exit codes 0/1/2/3 kyun? Sirf 0/1 se kaam nahi chalta tha?Sprint 2

Ye "killer" answer hai — zaroor yaad rakho:

ExitMeaningCI result
0Scan complete, policy passGreen
1Scan complete, policy violate (genuine security block)Intentional red
2Invalid CLI/config (galat threshold, invalid severity)Fail closed
3Operational failure (Trivy missing, registry/timeout/JSON/file error)Fail closed

Why it matters: agar sirf 0/1 hota, to ek broken scanner bhi build fail kar deta — aur team sochegi "image mein vulnerability hai". Isse false sense of security milti hai. Exit 3 alag hone se team turant samajh jaati hai ki problem scanner/infra mein hai, image mein nahi.

Ye distinction tests mein bhi cover kiya: exit 1 aur exit 3 ke alag test cases hain.

Trivy ka --exit-code kyun use nahi kiya?Sprint 2

Trivy ka --exit-code directly build fail kara sakta hai, lekin:

  • Uski failure "Trivy crash" aur "vulnerability found" mein farq nahi karti (same non-zero)
  • Policy phir CI YAML mein chali jaati — GitHub YAML aur Jenkinsfile mein duplicate logic, drift ka risk
  • Uske saath report generation/notification ka ordering manage karna mushkil hota (build turant fail, evidence generate nahi hota)

Isliye policy evaluation Python mein rakhi aur scanner hamesha --exit-code ke bina chalaya. Build ka final result hum khud decide karte hain — aur wahi exit code restore karte hain evidence collect karne ke baad.

Configuration precedence explain karo aur kyun aisa design kiya?Sprint 2 
CLI option  >  Environment variable  >  config.yaml  >  code default

Properties: har setting independently resolve hoti hai; chhota override bada default override karta hai.

Kyun:

  • Config file = team policy (reviewed, versioned)
  • Env var = CI/CD-specific override (jaise ek special pipeline sirf CRITICAL par block kare)
  • CLI = ad-hoc local testing without editing files
  • Defaults = fail-safe, agar kuch bhi na mile to bhi system chale

Invalid value par fail-closed — exit 2, silent fallback nahi. Kyunki security control mein silent default dangerous hai.

GitHub Actions workflow ke triggers aur steps samjhao.Sprint 2

Triggers: push (main + sprint branches), pull_request (main), workflow_dispatch (manual, image + threshold input), aur workflow_call (reusable — dusra workflow naya build kiya image hand over kar sakta hai).

Job steps (ek hi job "Vulnerability gate"):

  1. Checkout
  2. Python setup (cache enabled)
  3. Dependencies install
  4. Trivy pinned version install (cache)

GitHub Actions mein security considerations kya rakhe?Sprint 2

Jenkins agent par kya problems aayi aur kaise solve ki?Sprint 2

Academic Jenkins agent bahut minimal tha — teen issues mile:

  1. python3-venv installed nahi (aur sudo access nahi) → python3 -m venv fail ho gaya.
    Fix: pip install --target .ci-python se workspace-local dependency directory banayi, aur PYTHONPATH se use kiya — root ki zarurat nahi.
  2. Trivy preinstalled nahi → pipeline khud pinned tarball download karke .tools/ mein extract karta hai.
  3. Shell dash tha, bash nahi → mere pehle Sprint 3 script mein shopt aur arrays the, to exit 127 aaya.
    Fix: POSIX-compatible globbing (ls ... || true + string check) use kiya. Uske baad builds pehli baar mein pass hue.

Lesson: CI pipeline ko environment ke assumptions nahi karne chahiye — self-bootstrapping hona chahiye.

GitHub Actions aur Jenkins mein same policy kaise guarantee kari?Sprint 2

Kyunki policy logic kisi CI platform mein nahi hai. Dono platforms sirf ek hi command call karte hain:

python -m scanner.trivy_scanner "$SCAN_IMAGE"

Workflow YAML aur Jenkinsfile mein sirf orchestration hai — install, cache, run, archive. Severity counting, threshold aur exit code sab Python mein. Isliye same input par identical decision aata hai

Iska test bhi hai: dono platforms par humne green path (hello-world:latest) aur intentionally blocked path (alpine:3.19, 2 HIGH) demonstrate kiya.

Tests bina Docker/network ke kaise likhe?Testing

Do techniques use ki:

  1. Mocked subprocess: subprocess.run ko monkeypatch kiya, taaki actual Trivy na chale. Hum assert karte hain ki correct command bani (jaise --severity HIGH,CRITICAL, --ignore-unfixed present hai, image last argument hai).
  2. Synthetic fixtures: tests/fixtures/ mein hand-written Trivy JSON — trivy-pass.json (sirf LOW), trivy-fail.json (HIGH + CRITICAL), trivy-empty.json (null vulnerabilities). Real CVE data kabhi bhi badal sakta hai, isliye assertions fixtures par hain.

Isse kya mila: tests deterministic, fast (~3 seconds) aur CI mein her run par reliable — network flakiness nahi.

Coverage: command construction, parsing, invalid JSON, missing executable, precedence, strict booleans, policy boundaries, exit codes 0–3, artifact creation, multi-image failure priority.

--all-configured kya karta hai?Sprint 2

Bina argument ke, ye config.yaml ke images list ke saare images scan karta hai. Ye daily/weekly portfolio summary ke liye use hota hai.

Aggregation rules:

  • Kisi bhi image par operational error → exit 3 (highest priority)
  • Warna koi bhi image blocked → exit 1
  • Warna sab pass → exit 0

Yaani ek image ka failure baaki images ka result chhupata nahi — sab scan hote hain aur summary ban jaati hai.

Dono platforms mein evidence fail hone par bhi kaise bacha?Sprint 2

Ye "evidence-before-failure" pattern hai:

  • GitHub: scanner step exit code ko GITHUB_OUTPUT mein capture karta hai aur step success kar deta hai; reports upload if: always() ke saath hoti hain; aakhir mein ek step original exit code restore karta hai → build red lekin evidence maujood.
  • Jenkins: sh(returnStatus: true) se exit code variable mein rakha jaata hai; reports aur Slack uske baad chalte hain; Enforce Gate Result stage aakhir mein error() deta hai; post { always { archiveArtifacts } } evidence save karta hai.

Verified: Jenkins build #3 mein build FAILURE tha, phir bhi JSON+HTML+PDF+manifest archived mile.

Retry logic exactly kya hai?Sprint 3
  • Max 3 attempts, exponential backoff + jitter, total backoff capped (~30s)
  • Retry on: network/timeout errors, HTTP 408, 425, 429, aur 5xx
  • Honour Retry-After — but bounded (10s tak), taaki provider humein bahut der na rokе
  • No retry on other 4xx (400/401/403/404) — kyunki wo configuration/authorization problem hai; repeat karne se fayda nahi
  • Timeout: per-request 10 seconds
  • Exhausted → notifier exit 3 (operational failure), silent success nahi

Tests: transport, sleep aur randomness inject kiye — isliye tests fast hain aur kabhi Slack ko call nahi karte.

Webhook validation mein kaunse attacks consider kiye?Security

  • HTTPS only — plaintext par secret na jaaye
  • Host allowlist — sirf hooks.slack.com (aur hooks.slack-gov.com) — yaani arbitrary endpoint par data exfiltration nahi
  • Path prefix /services/ — valid webhook shape
  • Credentials reject — URL mein user:pass@ allow nahi
  • Fragment reject — #... se confusion avoid
  • Port 443 only — non-standard port se bypass na ho
  • Redirects refused — custom _NoRedirect handler; warna validation redirect ke through bypass ho jaati
  • Never logged — errors sanitized; URL/query/payload kabhi log nahi hote

Ye kya type ka risk hai: server-side request forgery (SSRF) jaisa behaviour aur secret leakage. Validation se attacker-controlled URL se data bahar nahi bheja ja sakta.

Allowlist/exception ki zarurat kyun hai? Bina uske kya problem?Sprint 5

Real world mein kuch vulnerabilities deliberately accept ki jaati hain:

  • Fix available nahi hai upstream (no fix version)
  • Not exploitable humari usage mein (jaise vulnerable code path use hi nahi hota)
  • False positive — package installed nahi ya detect galat hua
  • Compensating control lagaya hua hai (network isolation, WAF)

Bina allowlist ke: build permanently red rehta hai → team gate ko bypass karna shuru kar deti hai (continue-on-error, manual override). Yaani security control ka credibility khatam.

Sprint 5 mein retry/error handling kya add karoge? Sprint 2/3 mein nahi hai?Sprint 5

  • Distributed DB cache: shared volume ya OCI registry se Trivy DB serve karo
  • Remote write: Prometheus remote-write/Pushgateway se centralized metrics
  • Policy engine upgrade: OPA/Rego jaisi policy language, taaki complex rules (per-team exemptions) manage ho sakein
  • Queue + async: scan requests queue mein, worker pool
  • Storage: reports object storage (S3) mein, retention lifecycle ke saath

Lekin core design same rahega — scanner, report model aur notifier separate hain, isliye scaling orchestration layer mein hoti hai, core logic mein nahi.

H. Viva traps — mushkil sawaal aur safe jawab

Ye wo questions hain jinme examiner aapko test karta hai. Honest + confident rehna.

"Ye to bas Trivy ka wrapper hai" — kya bologe?Viva traps

Answer: "Trivy scanning engine hai, lekin project ka value uske aas-paas ke system mein hai:"

  • Policy engine: Trivy batata hai vulnerabilities kya hain; hum decide karte hain kaunsa finding build block karega, aur wo decision config-driven hai
  • Stable exit contract: Trivy ka non-zero exit code "policy block" aur "scanner crash" mein farq nahi karta — humara wrapper karta hai (0/1/2/3)
  • Normalisation: versioned schema 1.0 — isse aage reporting, dashboard aur audit possible hoti hai
  • Multi-platform consistency: ek hi command GitHub Actions, Jenkins aur local par — koi drift nahi
  • Reporting + delivery + governance: JSON/HTML/PDF with checksums, Slack alerts, aur (Sprint 5) exception management — ye Trivy nahi deta

Analogy bol sakte ho: "Trivy ek engine hai, humne usko poora vehicle banaya — policy, dashboard, brakes (gate) aur warning lights (alerts)."

Tumne sirf OS packages scan kiye — language dependencies miss ho rahi hain. Ye galat nahi?Viva traps

Accept karo, phir justify karo:

  • Sprint 1 mein ye deliberate tha — multiple base images ko fairly compare karne ke liye package scope fix karna zaroori tha
  • Ye config-driven hai (pkg_types: [os]) — ek line change se full scan ho jaata hai
  • Evidence bhi hai: node:18 scan mein jaise hi Java/npm analysis involve hua, scan heavy ho gaya (Java DB ~913 MB) — isliye scope control ki zarurat thi

Aage ka plan: "Sprint 6 mein production configuration pkg_types: [os, library] hogi, aur har image type ke hisaab se timeout tune karunga."

Trivy false positives dega to? Aapka gate galat block karega?Viva traps
  • Low false-positive rate par bhi possible hai — jaise vulnerable code path use nahi hota
  • Iska solution allowlist hai (Sprint 5): specific CVE, documented reason, expiry date ke saath approve karo
  • Saath hi severity tuning: agar MEDIUM noise kar raha hai to fail_on HIGH/CRITICAL rakho (by default wahi hai)
  • Suppressed findings report mein dikhte hain — silently chhupte nahi, isliye visibility poori rehti hai
Agar Trivy DB stale ya unreachable ho to?Viva traps

Fail-closed behaviour: DB download fail hone par scanner error throw karta hai → exit 3 → build fail. Ye intentional hai: "unknown" ko "safe" nahi maana jaata.

Practical handling:

  • CI mein DB refresh alag step hai (bounded retry ke saath) — taki transient network issue build block na kare
  • DB cache use hota hai, isliye repeat runs mein download ki zarurat nahi
  • Offline/air-gapped environment ke liye --skip-db-update option documented hai
  • Report mein scanned_at hota hai — agar DB purana tha, to staleness detect ho jaati hai
Private registry ke images kaise scan karoge?Viva traps
  • Trivy registry credentials support karta hai (TRIVY_USERNAME/TRIVY_PASSWORD ya docker config)
  • Design principle: credentials sirf CI secret/credential store se aayenge — config file mein kabhi nahi
  • Image reference mein credentials embed nahi karte (jaise user:pass@registry/image) — warna log aur artifact mein leak ho jaate
  • GitHub par masked secrets, Jenkins par credentials binding
Sprint 4 aur 5 abhi implement nahi hain — viva mein kaise defend karoge?Viva traps

Honesty + design clarity se defend karo:

"Sprint 1, 2 aur 3 complete aur verified hain — evidence ke saath. Sprint 4 aur 5 ka scope dashboard aur exception handling hai, aur unke liye required interfaces already bane hue hain:"
  • Sprint 4 ko Sprint 3 ka canonical report JSON chahiye — wo maujood hai, isliye exporter + Grafana wiring bacha hai
  • Sprint 5 ko exceptions/allowlist.yaml aur exceptions_file config key chahiye — structure design ho chuka hai
  • dashboard/ aur exceptions/ folders Sprint 1 se reserved hain — yaani plan upfront tha

Ye dikhata hai ki tum incremental delivery kar rahe ho, aur architecture aage ke sprints ke liye ready hai — jo assignment ka spirit hai.

Top 3 learnings kya rahe?Viva traps
  1. Security control ka credibility evidence par depend karta hai: agar build block hone par log/artifact na mile, team gate ko trust nahi karti. Isliye "evidence before failure" pattern banaya.
  2. "Fail" ke multiple meanings hote hain: vulnerability mila (exit 1) aur scanner toota (exit 3) — inko alag rakhna ek real security design decision hai.
  3. CI environment par assumptions nahi karne chahiye: Jenkins agent par na python3-venv, na Trivy, aur shell bash nahi dash tha. Pipeline ko self-bootstrapping banaya.
Agar examiner bole "dashboard banao bina Prometheus ke" — kya karoge?Viva traps

Do valid options present karo:

  1. Lightweight: Sprint 3 ki HTML report hi "latest state dashboard" hai — summary cards, per-image policy state, findings tables. No extra infra. (Ye already exist karta hai.)
  2. Custom UI: Flask/FastAPI + SQLite + Chart.js — reports ko ingest karke history table banayein. Isme humein storage, API, auth aur charts sab likhna padega — zyada code, less standard.

Recommendation: "Agar history aur trends chahiye to Prometheus + Grafana better engineering choice hai — kam code, better retention, standard tooling. Agar sirf latest status chahiye to Sprint 3 ki HTML report hi sufficient hai."
