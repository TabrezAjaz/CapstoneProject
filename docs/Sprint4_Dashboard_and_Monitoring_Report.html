Sprint 4: Dashboard and Monitoring

Tabrez Ajaz | Verified 29 October 2026 | Local, open-source deployment

1. Objective and Acceptance

Provide a usable historical view of image vulnerabilities, expose trustworthy metrics to Prometheus, and visualize them in Grafana. Filters must support specific images, date ranges, and severity. The dashboard must remain usable on desktop and mobile.

2. Architecture

Trivy -> schema 1.0 normalized scan artifact
          |-> existing JSON / HTML / PDF reports
          |-> validated, idempotent CLI importer -> SQLite history
                                                   |-> Flask API -> Chart.js UI
                                                   |-> /metrics -> Prometheus -> Grafana
CI runs -> normalized scan artifacts + reports/scan-metrics.prom -> archived evidence

The scanner stays a short-lived CLI. A separate long-running history service serves metrics after the scan exits. This replaces the earlier textfile-collector proposal with a persistent read-only exporter; Node Exporter and Pushgateway are not required.

CI jobs do not write to an unauthenticated public history endpoint. Download and import retained normalized artifacts into the local history store. Reimporting an unchanged scan ID does not inflate history; conflicting reuse is rejected transactionally.

5. Metric Definitions

MetricSemantics
vulnerability_findingsLatest active finding count per image/severity
vulnerability_blocking_findingsLatest active findings at/above the configured threshold
vulnerability_policy_blocked1 for blocked, 0 for passed
vulnerability_new_findingsAdvisory/package pairs not present in the previous scan
vulnerability_resolved_findingsPrevious pairs now absent from both active and suppressed findings
vulnerability_suppressed_findingsApproved exceptions, never counted as remediation
vulnerability_scan_timestamp_secondsActual latest scan time, independent of scrape time
vulnerability_scans_storedPersisted artifacts, expressed as a gauge
Counts and pair transitions measure different things: two scans can both contain ten findings while one advisory/package pair disappears and another appears. The implementation detects this instead of reporting a false zero change.

Found/resolved gauges describe the most recent transition per image, not cumulative events. The first observation is a baseline. An absent pair is an observation within the selected scanner scope, not independent proof of a patch. Policy blocking always reflects the full configured threshold, even if a severity display filter is selected.

8. Security, Retention and Limitations

  • All published Docker ports bind to 127.0.0.1; the HTTP API has no write routes.
  • SQL queries are parameterized. HTML is escaped, the UI inserts scan text safely, and the Flask service sets a restrictive Content Security Policy.
  • SQLite history and runtime secrets are excluded from Git and Docker build contexts. The dashboard container runs as a non-root user.
  • Prometheus retains 15 days from the start of scraping. It cannot retroactively reconstruct old time-series samples from SQLite. SQLite history persists until deliberately removed.
  • Operational scan failures are not fabricated as vulnerability scans. Stale-scan and exporter-down rules show missing coverage instead.
  • Existing hosted CI cannot reach a laptop's loopback service. Archived normalized artifacts must be imported locally; no remote central-store deployment is claimed.
  • This local demonstration uses Flask's development HTTP server. A public deployment requires production WSGI hosting, authentication, TLS and operational hardening.

9. Conclusion

Sprint 4 delivers persistent historical tracking, a usable custom dashboard, real Prometheus scraping, and a provisioned Grafana view. Evidence is derived from real normalized artifacts and tested with reproducible offline and browser checks. Sprint 5 adds governed exception handling and rescan/retry hardening to the same data contract.
